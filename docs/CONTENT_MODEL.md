# MyEngine Content Model

Status: Draft accepted for Phase 03  
Last updated: 2026-07-02

Content is data-driven from the beginning. This document defines the first model boundaries without
choosing a final parser format. JSON, TOML, YAML, or a custom authoring pipeline can be selected in
a later ADR, but the fields below are required concepts.

## Content Pack Manifest

Every pack has a manifest with:

- `schemaVersion`: integer content schema version.
- `packId`: stable lowercase identifier.
- `packVersion`: semantic or monotonically increasing content version.
- `engineCompatibility`: supported engine version range.
- `displayNameKey`: localization key, not hardcoded UI text.
- `dependencies`: pack IDs and version constraints.
- `entryPoints`: files or resources for definitions.
- `migrations`: optional migration scripts or declarative migration steps.
- `checksum`: optional package integrity value for release builds.

## Definition Rules

- IDs are stable and namespaced by pack.
- Definitions are immutable once loaded into a registry.
- Cross-references validate before simulation starts.
- Numeric fields include units where ambiguity is possible.
- Localization uses keys, not direct English strings in gameplay definitions.
- Game-specific content stays in game packs, not generic engine modules.

## Definition Families

### Tiles

Tiles describe terrain, movement cost, buildability, base render hints, tags, and optional resource
or hazard metadata. Tiles do not contain renderer-owned state.

### Entities

Entity definitions describe archetypes, stable component sets, persistence requirements, and
systems that may act on them. Runtime entity IDs are generated by simulation, not content.

### Towers

Tower definitions describe placement footprint, resource cost, targeting tags, cooldowns, effects,
upgrade hooks, and content references. They must not hardcode enemy names from reference games.

### Enemies

Enemy definitions describe movement tags, health model, resistances, reward hooks, and wave
participation. AI behavior references engine behavior contracts rather than embedded scripts in v1.

### Items And Resources

Resources describe stackability, storage tags, production/consumption units, localization keys, and
debug visualization hints. Balance values are content, not engine code.

### Recipes

Recipes describe inputs, outputs, duration in ticks, producer tags, power or worker requirements,
and failure rules. Recipe resolution must be deterministic.

### Waves

Waves describe spawn groups, timing in ticks, budget, eligible enemy tags, and scenario gates.
Randomized waves must use seeded simulation RNG.

### Incidents

Incidents describe triggers, budget, cooldowns, tags, target filters, and outcome hooks. The
storyteller chooses incidents through deterministic state and seeded RNG.

### Research And Upgrades

Research definitions describe prerequisites, costs, unlocks, modifiers, and localization. Research
must avoid copying reference game technology names or trees.

### Localization

Localization files map keys to text per locale. Missing keys fail validation in strict test mode and
warn in development mode only when explicitly allowed.

## Versioning And Migrations

- Content schemas start at version 1.
- Save files store pack IDs and versions.
- Removing or renaming IDs requires a migration entry.
- Migrations are tested with sample old content and save fixtures.
- Engine code must reject content that requires unsupported schema versions.

## Validation Gates

- Manifest is structurally valid.
- IDs are unique and namespaced.
- Cross-references resolve.
- Version and migration metadata is present.
- Numeric values are finite and within declared bounds.
- Localization keys exist for required locales.
- No Android or render backend classes appear in content model code.
